- 점검일: 2026-08-21 (KST)
- 점검 대상: `test.easy-scraping.com`, `easy-scraping.com`, 미니PC Docker 컨테이너, 관리자 화면, 공지/팝업, 로그인·상점·로또, 현재 워크스페이스 소스

## 1. 경영 요약

테스트·본서버 모두 최종 시점에는 Docker `healthy`, restart 0이며 외부 홈·헬스·readiness가 200이다. 그러나 최신 테스트 이미지에서 관리자 공지 목록/등록 API와 공개 팝업 API가 누락되어 404를 반환한다. 관리자 화면에는 공지 등록 폼이 보이지만 실제 등록이 되지 않고, Discord 명령으로 공지를 생성해도 기본 홈 팝업이 표시되지 않는다. 따라서 “테스트 서버 QA 통과 후 본서버 배포” 조건을 만족하지 못했다.

테스트 서버는 점검 중 이미지가 여러 번 교체됐다. 16:52경 이전 이미지에서는 로그인·상점·로또·공지·Discord 공지 명령까지 통합 QA를 모두 통과했으나, 이후 `adminRoutes.js` 문법 오류와 `spendingRoutes.js` 경로 호환 오류로 두 번 재시작 루프/502가 발생했다. 현재 실행 이미지는 기동 오류를 해결했지만 공지 라우트가 빠진 기능 회귀 상태다.

본서버는 가용성과 기존 공지 팝업이 정상이다. 다만 테스트·본서버 모두 비로그인 상점이 활성 구매 버튼을 보여 주며 로그인 필요 메시지가 없다. 본서버에는 메인 통계·부자 순위 표시 오류, 음수 국고 노출, 특정 사용자 전용 감사 화면 하드코딩도 확인됐다. 구매 API 자체는 양쪽 모두 비로그인 요청을 401로 차단하므로 현재 확인된 것은 인증 우회가 아니라 UI 로그인 상태 표시 결함이다.

## 4. 결함 목록

### QA-P0-001 — 최신 테스트 이미지에서 공지 API·팝업 API 누락

- 심각도: **P0 / 릴리스 차단**
- 재현:
  1. 관리자 세션으로 `/admin/announcements` 접속 → `/admin/console#announcement-manager`로 이동하고 등록 폼 표시
  2. 관리자 GET `/api/admin/announcements` → 404
  3. 관리자 POST `/api/admin/announcements` → 후순위 CSRF 라우터가 가로채 403
  4. Discord `/admin_notice`로 임시 팝업 공지 생성 → 명령과 DB 생성은 성공
  5. `/api/announcements/popup` → 404, 기본 홈 다이얼로그 미표시
- 원인: 최신 테스트 이미지의 `adminRoutes.js`에서 공지 CRUD 라우트가 누락됐고, `server.js`의 후순위 관리자 관리 라우터가 `/api/admin` 전체에도 중복 마운트돼 미등록 POST에 403 CSRF 오류를 반환한다. 공개 팝업 조회 라우트도 누락됐다.
- 추가 회귀: 테스트 `/shop`에는 공지 팝업 스크립트와 Socket.IO 스크립트가 포함되지 않았다.
- 영향: 관리자 페이지와 Discord 명령 어느 경로로 공지를 만들어도 테스트 웹에 팝업을 표시할 수 없다. 사용자가 제보한 “공지 등록/팝업이 안 됨”을 그대로 재현했다.
- 조치 권고: 본서버 이미지에 존재하는 공지 CRUD와 공개 팝업 라우트를 최신 코드로 복원하고, 잘못된 광역 admin-management 마운트를 제거한다. 홈·상점 E2E에서 생성 → API 조회 → 다이얼로그 → 삭제를 필수 검사한다.

- 심각도: **P0 / 배포 파이프라인 결함**

  - 16:58경: `adminRoutes.js:2867`의 `SyntaxError: missing ) after argument list`로 재시작 루프
  - 17:03경: 새 테스트 이미지에서도 `Unexpected ?` 라우트 오류로 재시작 루프
  - 17:21~17:25경: 이미지가 추가 교체됐으나 공지 CRUD·공개 팝업 라우트 누락으로 기능 QA가 동일하게 FAIL
- 영향: 문법/애플리케이션 부팅 검사가 이미지 승격 전에 실행되지 않아 연속으로 기동 불가능한 이미지가 테스트 트래픽에 연결됐다.
- 조치 권고: 이미지 빌드 후 `node --check`, 실제 서버 import/boot smoke, `/readyz` 확인을 배포 스크립트의 필수 게이트로 추가한다. 실패 시 기존 healthy 이미지 유지 또는 자동 롤백이 필요하다.

### QA-P1-003 — 비로그인 상점이 로그인 사용자인 것처럼 보임

- 심각도: **P1 / 인증 상태 UX**
- 재현:
  1. 로그아웃 상태로 테스트·본서버 `/shop` 접속
  2. 테스트는 잔액 0원, 본서버는 10,000원을 표시하지만 양쪽 모두 활성 `구매하기` 버튼과 확성기 버튼을 노출
  3. 구매 API를 호출하면 401 `로그인이 필요합니다.` 반환
- 원인: 본서버 템플릿은 비로그인 잔액 0을 기본 정착금 10,000원으로 대체해 표시하며 로그인 상태를 명확히 분기하지 않는다. 현재 워크스페이스의 `shop.ejs`도 `Number(userCash || 10000)` 형태의 fallback을 유지하고 있어 값 타입에 따라 0원 또는 10,000원으로 달라질 뿐, 비로그인 안내와 버튼 비활성화는 여전히 없다. 즉 이미지·소스 간 세부 차이와 무관하게 인증 상태 UI 설계가 누락돼 있다.
- 영향: 사용자는 로그인된 것으로 오인하고 구매 시점에만 실패 팝업을 본다. 이전에 제보된 “로그인 감지 못함” 증상과 일치한다.
- 보안 판정: 서버 구매 API는 401로 차단되어 **확인된 인증 우회는 없다**.
- 조치 권고: `user` 존재 여부로 화면을 분기하고 비로그인 시 잔액 대신 `로그인 필요`, 구매 버튼 비활성화, Discord 로그인 CTA를 표시한다.

### QA-P1-004 — 메인 화면 활동 유저·부자 순위 데이터 매핑 오류

- 심각도: **P1 / 운영 데이터 신뢰성**
- 운영 관측:
  - 활동 유저 `10,000`
  - 부자 순위 1위 2원, 2·3위 10,000원
- 원인 1: `landingPage.js`가 활동 유저 수 대신 리더보드의 최대 `net_worth` 또는 `cash` 값을 사용한다.
- 원인 2: DB 쿼리는 순자산을 `AS net`으로 반환하고 `ORDER BY net DESC`로 정렬하지만, 렌더러는 `user.net_worth || user.cash`를 표시한다. 즉 정렬 기준과 표시 기준이 다르다.
- 조치 권고: 실제 사용자 수를 별도 집계하고, 순자산 별칭을 `net_worth`로 통일한다. 회귀 테스트에 “순자산 정렬값 = 표시값” 검증을 추가한다.

### QA-P1-008 — 자동 채굴이 설계보다 과도하게 통화를 생성할 가능성

- 심각도: **P1 / 경제 인플레이션**
- 정적 근거:
  - 주석에는 최근 6시간 활동 유저만 지급한다고 되어 있으나 조회 조건은 `auto_miner_level > 0`뿐이다.
  - 밸런서는 `clickerYieldMultiplier`를 제공하지만 자동 채굴은 존재하지 않는 `autoMinerMultiplier`를 읽는다.

  - 30틱마다 `earnings_pool`에 고정 10,000,000과 계산 금액을 누적한다.
- 영향: 비활성 계정까지 무기한 발행되고 기업 실적/배당 풀이 급증해 인플레이션 제어가 무력화될 수 있다.
- 조치 권고: 최근 활동 제한, 올바른 동적 배율, `totalPaidThisTick / 10`, 고정 10,000,000 제거 여부를 설계와 대조한다.

### QA-P1-009 — 경제 흐름 모니터와 migration 009 스키마 불일치

- 심각도: **P1 / 모니터링 오판**

- 조치 권고: `flow_type`과 `created_at`으로 통일하고 쿼리 실패를 경고/헬스 지표로 노출한다.

### QA-P1-010 — 로또 원장이 30%가 아닌 티켓 가격 100%를 소각으로 기록

- 심각도: **P1 / 회계·경제 지표**
- 증상: 실제 로직은 티켓 가격의 30%를 소각하고 70%를 잭팟에 넣지만, `economy_flow_logs`에는 전체 티켓 가격을 `OUTFLOW_SINK`로 기록한다.
- 영향: 소각량이 실제보다 3.33배 크게 집계되고 순발행/인플레이션 지표가 왜곡된다.
- 조치 권고: 30%만 소각 원장에 기록하고 70%는 잭팟 준비금/내부 이전 원장으로 분리한다.

### QA-P2-011 — 상장 종목 안내 문구와 실제 데이터 불일치

- 심각도: **P2 / 콘텐츠 정확성**
- 운영 관측: 실제 상장 종목 통계는 46개인데 히어로·기능·메타 설명은 18개로 고정돼 있다.
- 조치 권고: 실제 종목 수를 한 곳에서 계산해 모든 문구에 동일하게 사용한다.

### QA-P2-012 — 본서버에 신규 소비 시스템 관리자 기능 미배포

- 심각도: **P2 / 환경 드리프트**
- 운영 결과: 기존 관리자 페이지는 200이지만 `/admin/spending`과 신규 spending 관리자 API는 404다.
- 의미: 현재 본서버는 새 소비 시스템이 포함된 테스트/워크스페이스 버전보다 오래된 이미지다. 테스트 서버가 실패한 상태에서 이 기능을 본서버에 승격하면 안 된다.

## 5. 관리자·공지 QA

| 항목 | 결과 |
|---|---|
| 비로그인 `/admin/users` | 403, 정상 |
| 인증된 `/admin/users`, `/admin/economy`, `/admin/console`, `/admin/security`, `/admin/inquiries`, `/admin/logs` | 200 |
| `/admin/announcements` | 302 → `/admin/console#announcement-manager` |
| 관리자 콘솔 공지 등록 폼 | 테스트·본서버 모두 존재 |
| 공지 목록 API | **테스트 404**, 본서버 200 |
| 공지 등록 API | **테스트 403/라우트 누락**, 본서버 라우트 존재 |
| 공개 팝업 API | **테스트 404**, 본서버 200 |
| 기본 홈 팝업 | **테스트 표시 실패**, 본서버 실제 공지 다이얼로그 표시 |
| `/shop` 공지 연결 | **테스트 스크립트 누락**, 본서버 팝업 표시 |
| Discord `/admin_notice` | 테스트 최신 이미지에서 생성·DB 확인·삭제 PASS |

공지 등록 버튼/진입점은 양쪽 관리자 화면에 보인다. 그러나 테스트 서버는 실제 API가 누락돼 폼만 있고 동작하지 않으며, 기본 홈 팝업도 표시되지 않는다. 본서버는 기존 공지 API와 팝업이 정상이다. 따라서 테스트 이미지를 본서버에 올리면 현재 정상인 본서버 공지 기능이 회귀한다.

## 6. 보안·로그 QA

본서버에서 확인된 정상 항목:

- HSTS `max-age=15552000; includeSubDomains`
- CSP `frame-ancestors 'none'`
- `X-Frame-Options: DENY`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy`로 위치·마이크·카메라 차단
- 비로그인 관리자 403, 비로그인 구매 401
- Discord OAuth 운영 콜백 URL 정상
- 컨테이너 read-only root filesystem과 비root 사용자 실행 확인
- 본서버 시작 이후 최근 로그에서 실제 예외, DB 오류, 5xx 패턴 미검출

## 7. 배포 승인 조건

현재 본서버 추가 배포는 승인할 수 없다. 다음 조건을 순서대로 모두 만족해야 한다.

1. 테스트 이미지에 본서버의 공지 CRUD·공개 팝업 라우트를 복원하고 `/api/admin` 중복 광역 마운트를 정리한다.
2. 배포 스크립트가 컨테이너 `healthy`와 외부 `/readyz` 200을 확인하기 전에는 트래픽을 전환하지 않게 한다.
3. `qa_test_server.sh`를 현재 CSRF/라우트 구조에 맞춰 보완하고 로그인·구매·로또·관리자 공지·공개 팝업·Discord 공지·보안을 전부 PASS시킨다.
4. 비로그인 상점 UI, 메인 통계/랭킹, 출석 오류, 자동 채굴, 경제 모니터, 로또 원장 결함을 수정하고 회귀 테스트를 추가한다.
5. 테스트 서버에서 최소 15분 동안 restart 0, OOM false, `/readyz` 연속 200, 오류 로그 0을 확인한다.
6. 동일 이미지 ID를 본서버에 승격하고, 배포 직후 헬스·로그·공지·로그인·관리자 읽기 QA를 반복한다.

## 8. 점검 제한 및 데이터 변경 여부

- 본서버에서는 실제 구매, 공지 생성/삭제, 관리자 변경 등 쓰기 작업을 수행하지 않았다.
- 테스트 서버 통합 QA는 임시 계정·구매·공지 데이터를 만들었으나 스크립트가 종료 시 정리했다.
- 실제 Discord OAuth 로그인을 새로 수행하지 않고 세션/API 경로와 테스트 계정 로그인으로 검증했다.
- 로컬 MySQL이 없어 실DB 동시성 테스트 1개가 스킵됐다. 테스트 DB를 사용한 별도 동시성 검증이 필요하다.
- 워크스페이스에는 다수의 미커밋 변경이 있어 Git HEAD와 테스트/본 이미지가 서로 다른 상태다. 최종 배포 전 소스 커밋과 이미지 ID의 추적 가능성을 확보해야 한다.
- 점검 중 테스트 이미지가 여러 번 자동 교체됐다. 최종 판정은 마지막 확인 이미지 `096205cd8654…` 기준이며, 이 이미지에서도 통합 QA가 6단계에서 동일하게 실패했다.
